## Blocking finding 1 — nonmonotone Wald coverage is still routed through a monotone-contiguous algorithm

`coverage_from_intervals()` explicitly implements coverage for “monotone contiguous acceptance sets” and obtains `first,last` using `np.searchsorted(lower/upper, p)`. This requires endpoint arrays sorted in `x`.

CP06-B already established that Wald has endpoint monotonicity failures (`2047` lower and `2047` upper for B). CP-04 §7.3 requires that any method violating endpoint monotonicity **must not be forced into a contiguous range**; `A(p)` must be enumerated explicitly and the structural anomaly recorded.

Therefore Wald coverage, worst-case rows, and any derivative evidence produced by the current generic path are not admissible as CP-06 evidence until a method-aware/nonmonotone-safe route is implemented.

This also means the prior CP06-B PASS must be narrowed: Wilson/Clopper–Pearson/Jeffreys numerical/oracle evidence remains usable, but Wald coverage evidence must be regenerated after the harness correction.

## Blocking finding 2 — E does not persist the required noncontiguous acceptance representation/search provenance

Checkpoint E calls the same generic `calibrate_n()` with `include_base_grid=False`. Its `worst_cases` schema records only `first_x` and `last_x`; it does not preserve an explicit acceptance set/runs for nonmonotone methods and does not record the requested search provenance (`search_method`, `optimizer_status` or analytic-stationary classification beyond point origin).

CP-04 §7.4 requires the global minimum, its `p`, the covering set/range of `x`, distance from nominal, and whether the minimum comes from a boundary/root/grid, with float64 and high-precision follow-up where required.

E therefore needs a dedicated adversarial-minimum artifact/schema rather than relying only on the generic `worst_cases` output.

## Blocking finding 3 — cache provenance is keyed only by production candidate SHA

`CACHE_ROOT` is currently namespaced only by `CANDIDATE_SHA`. A harness semantics change can therefore silently reuse pickles generated by an older harness implementation. C explicitly reuses B cache.

Because the next correction changes coverage semantics and output schema, old B pickles must not be silently accepted. Cache payload/path needs a harness/schema version and validation of producer/spec metadata, or the affected cache must be invalidated deterministically.

After correction, CP06-B must be rerun (or regenerated) for affected evidence before C consumes it.

## Required CP-04 item missing from current summaries — Wald pathology probabilities

CP-04 §6 and §11.3 require, in addition to coverage:

- `P_outside = P(lb < 0 or ub > 1)`
- `P_degenerate = P(ub == lb)`

The current generic summary records endpoint `bounds_failures` counts, but does not compute the probability mass of those outcomes as a function of true `p`. Counts are not a substitute for the preregistered probability metrics.

Add deterministic Wald pathology probability outputs/summaries and preserve them in checkpoint artifacts.

## Scalability concern — D/E recompute full production grids through per-x Python API calls

`production_interval_grid()` calls `PopulationProportionCI.from_counts(...).calculate_interval()` for every `x=0..n`, each alpha and each production method. At `n=1,000,000`, this implies roughly 21 million production API evaluations for that `n` alone. E then rebuilds the same interval grids because C/D do not persist reusable endpoint grids.

This is not automatically a correctness defect, but it is a material execution-risk against CP-04 §19 (bounded memory, reproducible sharding, avoid unnecessary giant work). Before Quantum runs D/E, the harness must demonstrate an execution strategy that avoids gratuitous recomputation and remains semantically tied to the frozen production API.

Acceptable strategies include a validated reusable endpoint cache with hashes/schema provenance, or another deterministic optimization whose equivalence to the production API is tested on a preregistered subset. Do not alter production code.
